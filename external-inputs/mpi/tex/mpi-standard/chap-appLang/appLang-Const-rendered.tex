\chapter{Language Bindings Summary}
\mpitermtitleindex{language binding!summary}
\label{sec:lang}
\label{chap:lang}
\label{chap:binding}

In this section we summarize the specific bindings for 
C and Fortran.
First we present the constants, type definitions, info values and keys. Then we present the routine prototypes separately for each binding.
Listings are alphabetical within chapter.

All ABI values must be cast to the appropriate type if the type of the constant
is not a C \ctype{int} or Fortran \ftype{INTEGER}.
For example, when \mpiconst{MPI\_COMM\_WORLD} is said to be 257,
the implementation will use \code{((MPI\_Comm)257)} in C.

\section[Summary of the Semantics of all Op.-Related Routines]{Summary of the Semantics of all Operation-Related \texorpdfstring{\MPI/}{MPI} Procedures}
\label{sec:lang:semantics:summary}

This annex 
provides the list of \MPI/ procedures that are associated with an \MPI/ 
operation, or inquiry procedures providing information about an operation.

In many cases, the \MPI/ procedures and their properties are listed under certain constraints,
e.g., a call to \mpifunc{MPI\_WAIT} that completes either a nonblocking or a persistent operation,
or \RMA/ calls in combination with various synchronization methods.

\paraheading{Table Legend:}
{\small
\begin{itemize}
\item \textbf{Stages:} \mpilegend{i}=initialization, \mpilegend{s}=starting, \mpilegend{c}=completion, \mpilegend{f}=freeing.
  The procedure does at least part
  of the indicated stage(s).
\item \textbf{Cpl:} \mpilegend{ic}=incomplete procedure, \mpilegend{c}=completing procedure, \mpilegend{f}=freeing procedure
\item \textbf{Loc:} \mpilegend{l}=local procedure, \mpilegend{nl}=non-local procedure
\item \textbf{$*$}: exceptions, e.g., \mpilegend{ic+nl} = incomplete+non-local, and \mpilegend{c+l} = completing+local (both are defined as blocking)
\item \textbf{Blk:} \mpilegend{b}=blocking procedure, \mpilegend{nb}=nonblocking procedure. Note that from a user's view point, this column is only a hint. Relevant is,
         whether a routine is local or not and which resources are blocked until when. See both previous and last columns.
\item  \textbf{$\ddagger$}: exceptions, e.g., nonblocking procedures without prefix \mpicode{I}, or that prefix \mpicode{I} only marks immediate return.
\item \textbf{Op:} part of operation type: \mpilegend{b-op} = blocking operation,
 \mpilegend{nb-op} = nonblocking operation, \mpilegend{p-op} = persistent operation,
 \mpilegend{pp-op} = persistent partitioned operation
\item \textbf{Collective procedures:}
\begin{itemize}
     \item \mpilegend{C} = all processes of the group must call the procedure
     \item \mpilegend{sq} = in the same sequence
     \item \mpilegend{S1} = blocking synchronization, i.e., no process shall return from this procedure
                      until all processes on the associated process group called this procedure
     \item \mpilegend{W1} = the implementation is permitted to do S1 but not required to do S1
     \item \mpilegend{S2} = start-complete-synchronization, i.e., no process shall complete the associated operation
                      until all processes on the associated process group have called the associated starting procedure
     \item \mpilegend{W2} = the implementation is permitted to do S2 but not required to do S2
\end{itemize}
%
\item \textbf{Blocked resources:} They are blocked after the call until the end of the subsequent stage where this resource is not mentioned further in the table.
\end{itemize}
}

\paraheading{Table Remarks:}
{\small
\begin{enumerate}
\item \label{semantics:item1} Must not return before the corresponding \MPI/ receive operation is started.
\item \label{semantics:item2} Not related to an \MPI/ operation.
Prior to \MPIIVDOTO/, \mpifunc{MPI\_PROBE} and \mpifunc{MPI\_IPROBE}
were also described as blocking and nonblocking.
From \MPIIVDOTO/ onwards, only non-local and local are used to describe these procedures.
\item \label{semantics:item3} Usually, \mpifunc{MPI\_WAIT} is non-local, but in this case it is local.
\item \label{semantics:item4} In case of a \mpiskipfunc{MPI\_(I)BARRIER}\mpifuncindex{MPI\_BARRIER}\mpifuncindex{MPI\_IBARRIER} on an intra-communicator,
      the \mpilegend{S1/S2} synchronization is required (instead of W1/W2).
\item \label{semantics:item5} Collective: all processes must complete, but with the free choice of using \mpifunc{MPI\_WAIT}
     or \mpifunc{MPI\_TEST} returning \mpiarg{flag}\code{ = TRUE}.
\item \label{semantics:item6} It also may not return until \mpifunc{MPI\_INIT} was called in the children.
\item \label{semantics:item7} Addresses are cached on the request handle.
\item \label{semantics:item8}
One of the rare cases that an incomplete call is non-local and therefore blocking.
\item \label{semantics:item9} One shall not free or deallocate the buffer before the operation is freed, that is \mpifunc{MPI\_REQUEST\_FREE} returned.
\item \label{semantics:item10} For \mpifunc{MPI\_WAIT} and \mpifunc{MPI\_TEST}, see corresponding lines for a) \mpifunc{MPI\_BSEND}, or b) \mpifunc{MPI\_IBCAST}.
\item \label{semantics:item11}
The prefix \mpicode{I} marks only that this procedure returns immediately.
\item \label{semantics:item12}
One of the exceptions that a completing and therefore blocking operation-related procedure is local.
\item \label{semantics:item13} \mpiskipfunc{MPI\_(I)MPROBE}\mpifuncindex{MPI\_MPROBE}\mpifuncindex{MPI\_IMPROBE}
      initializes the operation through generating the message handle
      whereas
      \mpiskipfunc{MPI\_(I)MRECV}\mpifuncindex{MPI\_MRECV}\mpifuncindex{MPI\_IMRECV}
      initializes the receive buffer
      (i.e., two \MPI/ procedures together implement the initialization stage).
\item \label{semantics:item14} Nonblocking procedure without an \mpicode{I} prefix.
\item \label{semantics:item15} Initialization stage (``\mpilegend{i}'') only if \mpiarg{flag}\code{ = TRUE} is returned else no operation is progressed.
\item \label{semantics:item16} Collective: all processes must start, but with the free choice of using \mpifunc{MPI\_START}
     or \mpifunc{MPI\_STARTALL} for a given persistent request handle
     (i.e., if one process starts a persistent request handle then all processes
     of the associated process group must start their corresponding request handle,
     and if any process starts then all processes must complete their handles).
\item \label{semantics:item17} In a correct \MPI/ program, a call to \mpifuncskip{MPI\_(I)RSEND} requires
that the receiver has already started the corresponding receive.
Under this assumption, the call to \mpifunc{MPI\_RSEND} and the call to
\mpifunc{MPI\_WAIT} with an (active) ready send request handle are local.
\item \label{semantics:item18} Based on their semantics, when called using an intra-communicator, \mpifunc{MPI\_ALLGATHER},
     \mpifunc{MPI\_ALLTOALL}, and their \mpiskipfunc{V} and \mpiskipfunc{W}
     variants, \mpifunc{MPI\_ALLREDUCE}, \mpifunc{MPI\_REDUCE\_SCATTER}, and  \mpifunc{MPI\_REDUCE\_SCATTER\_BLOCK}
     must synchronize (i.e., \mpilegend{S1/S2} instead of  \mpilegend{W1/W2}) provided that all counts
     and the size of all datatypes are larger than zero.
\item \label{semantics:item19} \mpifunc{MPI\_COMM\_FREE} may return
  before any pending communication has finished and the communicator
  is deallocated. In contrast, \mpifunc{MPI\_COMM\_DISCONNECT} waits
  for pending communicaton to finish and deallocates the
  communicator before it returns. 
\item \label{semantics:item20} The request handle is in the ``active'' state after \mpifunc{MPI\_START}, i.e., \mpifunc{MPI\_REQUEST\_FREE} is now forbidden.
But the starting stage is not yet finished, and the contents of the buffer are not yet ``blocked.''
An additional \mpifunc{MPI\_PREADY} and variants \mpiskipfunc{MPI\_PREADY\_RANGE}\mpiskipfunc{MPI\_PREADY\_LIST}
are required to activate each partition of the send buffer to finish the starting stage.
\item \label{semantics:item21} As part of the completion stage, the user is allowed to read part of the output buffer after returning
from \mpifunc{MPI\_PARRIVED} with \mpiarg{flag}\code{ = TRUE} before completing the whole operation with a \mpifunc{MPI\_WAIT}/\mpifunc{MPI\_TEST} procedure.
\item \label{semantics:item22} It initializes the attached buffer as completely free.
\item \label{semantics:item23} It uses the attached buffer and performs all four stages on the send buffer. It occupies the needed part of the attached buffer. 
\item \label{semantics:item24} It waits until the attached buffer is empty, i.e., all messages have been transmitted, and then releases the attached buffer.
\item \label{semantics:item25} Although in case of \mpiarg{flag}\code{ = TRUE} the operation is completed,
  a subsequent call to test, wait, or free must be executed for deallocating or inactivating
  the request handle as final part of the stages c and f. It is listed only in this scenario,
  but can be used everywhere, where \mpifunc{MPI\_TEST} can be called.
\item \label{semantics:item26} It frees the request handle. If the related communication
  operation is still ongoing then the completion and freeing stage can take place after the
  procedure returned.
\item \label{semantics:item27} Cancelling a send request is deprecated.
\item \label{semantics:item28} Can also be applied to activ persistent requests.
\item \label{semantics:item29} As an exception, \mpifunc{MPI\_WAIT} is local and
  \mpifunc{MPI\_TEST} repeatedly called will eventually return \mpiarg{flag}\mpicode{=true}.
  The cancelled send or receive operation is completed and the buffer can be reused. Whether the message is sent out from the buffer or received in the buffer, this part of the completion stage is only executed if a subsequent
  \mpifunc{MPI\_TEST\_CANCELLED} for the returned status would
  return \mpiarg{flag}\code{ = FALSE}.
  The freeing stage will be performed only for non-persistent requests.
\item \label{semantics:item30} In some cases, more than one \MPI/ procedure may be 
  needed to implement one stage of an \MPI/ one-sided operation.
  For details on the semantics of one-sided operations, see \namedref{Chapter}{sec:one-side-2}.
\item \label{semantics:item31} Local completion only (at origin).
\item \label{semantics:item32} Local completion only (at target).
\item \label{semantics:item33} Completion at target and locally at origin.
\item \label{semantics:item34} Return from \mpifunc{MPI\_WIN\_START} and these
  subsequent procedures at the origin process may be delayed until \mpifunc{MPI\_WIN\_POST}
  has been called at the target process (see \sectionref{sec:1sided-sync}
  and \namedref{Example}{ex:1sided-start-complete}).
\item \label{semantics:item35} Return from \mpifunc{MPI\_WIN\_LOCK} and these
  subsequent procedures may be delayed until other origin processes have released
  their lock (see \sectionref{sec:1sided-sync} and \namedref{Example}{ex:1sided-lock-unlock}).
\item \label{semantics:item36} The init and freeing stages and the buffer address of
  the target window only apply to \mpi/ processes in the role of a target of an \RMA/ operation.
\item \label{semantics:item37} The freeing stage applies to operations only
  and does not apply to any request.
\item \label{semantics:item38} The same procedure call may serve different
  stages for different operations, i.e.,
  the completion of a previous \RMA/ and/or exposure epoch and/or
  the start of a next \RMA/ and/or exposure epoch.
\item \label{semantics:item39} In addition to the completion and freeing of
  the \RMA/ operations prior the the flush call (stages ``\mpilegend{c+f}''),
  this call initializes the next \RMA/ epoch (stage ``\mpilegend{i}'').
\item \label{semantics:item40} The stages represent the invocation as part of an \RMA/ operation.
  As collective procedure itself, it is a blocking procedure with all stages.
\end{enumerate}
}
