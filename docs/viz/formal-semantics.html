Inside semantics.formal

An operational data-flow and synchronization layer, added underneath the existing classification fields, precise enough that a code generator can emit an actual transfer from it and a verifier can turn it into a proof obligation — including where the data actually lives — without either one parsing a sentence of prose.

0x0

Why This Layer Exists

The existing eight sections tell a tool what kind of call something is. They don't say who touches what memory, in what order, relative to whom — and that second thing is what a code generator or a verifier actually needs.

semantics.collective.type = "broadcast" is enough for a human reading documentation. It is not enough for a tool to emit the actual transfer, or to write down the obligation that a race detector checks. Compare the two states of knowledge for mpi:mpi_bcast:

Before — classification onlyAfter — semantics.formal
"This is a collective, type broadcast, root involved, not in-place." "The root reads count elements of datatype from buffer; every non-root participant writes the same extent into its own buffer, and that write's value is exactly the root's read; no participant returns until every participant has entered."

The right-hand column is a sentence a tool can act on: a code generator lowers it directly into a transfer primitive, a verifier lowers it directly into a data-equality obligation plus a collective-matching check. semantics.formal is that column, formalized as JSON instead of prose — added as a fourth field alongside the existing operation_class/collective/point_to_point/one_sided/atomic/memory fields, and left null wherever an entry doesn't need it (query calls, most management ops — their correctness is already fully carried by execution.stages and tool_integration.invariants).

Design constraint carried over from the rest of the spec: everything below stays inside a closed, enumerable vocabulary — no predicate parser, no quantifiers, no embedded logic language. A consumer implements against a fixed set of field names and a fixed set of enum values, once, regardless of how many PPM entries populate formal.

Anatomy of semantics.formal

Four sub-fields. Each one answers a different question about a call.

FieldQuestion it answersPresent when
participantsWho is involved, and does each one actually invoke the function?Always, whenever formal is non-null
data_flowWho reads, writes, or reduces which memory, and where does a written value come from?Communication ops; empty array for pure-sync ops (barrier)
syncWhat ordering must hold between participant instances, and how are separate call instances matched to each other?Always, whenever formal is non-null
handle_lifecycleDoes this call create, use, or destroy a long-lived handle (request, window, communicator, symmetric-heap allocation)?Handle-bound ops; empty array otherwise

participants

A list of roles a single call instance can be decomposed into. calls_function matters more than it looks: it's false for the passive side of a one-sided operation — the target of an mpi_put never calls anything, and a static analyzer that assumes every participant has a matching call site will misfire on exactly this case.

{
  "id": "root",
  "role_kind": "initiator",
  "calls_function": true,
  "cardinality": "one",
  "selector": "rank == param:root"
}
FieldTypeNotes
idStringReferenced by data_flow[].participant and sync.events[].participant
role_kindEnum"initiator"｜"member"｜"passive_target"
calls_functionBooleanfalse for RMA/atomic targets
cardinalityEnum"one"｜"many"
selectorStringPredicate in the shared reference grammar, see below

data_flow

One entry per memory access. Four op values cover every case seen so far: "read", "write", "reduce" (an aggregation node with no single participant — its inputs is a scoped set of sibling reads), and "read_modify_write" (atomics). The field that actually carries verification/codegen value is source — a tagged object saying where a written value provably came from:

source.kindMeansExample op
structuralCopy from a named sibling data_flow entry in the same call instancebcast, put
reducedAggregation over a scoped set of sibling reads across all participant instancesallreduce, scan
matchedResolved at runtime by a sync.matching rule against a separate call instanceirecv
nullComes from implementation/runtime state — not modeledquery calls
{ "id": "df_write", "participant": "non_root", "op": "write",
  "buffer": "param:buffer",
  "extent": { "count_ref": "param:count", "datatype_ref": "param:datatype" },
  "offset": null,
  "source": { "kind": "structural", "ref": "df_read" } }

offset is null for uniform-copy shapes (bcast) and a reference-grammar expression for indexed shapes (scatter — each participant's slice is offset by its rank).

Notice data_flow says what gets read or written but nothing about which kind of memory — host RAM, device memory, a symmetric heap. That's a property of the referenced parameter, not of the access, so it lives on parameters[].memory_space instead of being duplicated here. See 0x8 — GPU Memory Spaces.

sync

Three parts. events are named points (or interval endpoints — see epochs, next section) tied to a participant and optionally bound_to a handle parameter. ordering states happens-before relationships between events, scoped to same_participant_instance, all_participant_instances, or cross_call. matching states how separate call instances pair up:

matching.kindPairs instances byUsed by
collective_rendezvousEvery instance in the participant group, no key neededbcast, barrier, allreduce
tag_matchcomm + tag + source/dest, non-overtakingMPI isend/irecv
peer_matchcomm + peer rank, program order within a group, no tagNCCL send/recv
group_matchset equality/overlap of an explicit process groupMPI PSCW epochs
epoch_scopeddeferred to an enclosing epoch — no matching at this call siteRMA put/get inside a lock/fence region

handle_lifecycle

Tracks a handle (request, window, communicator, symmetric-heap allocation) across its create → use → destroy interval. Covered in full in the next section, since it's what makes RMA epochs and resource lifecycle work under one mechanism instead of two.

reference & selector grammar

One small, closed grammar, reused everywhere a predicate or a reference is needed — the same expression style tool_integration.invariants already uses, just formalized once instead of ad hoc per field.

rankThe calling process/PE's rank

rank_in(comm_ref)This rank's index within a communicator/team
is_neighbor(rank, comm_ref)True if rank is a topology neighbor under comm_ref's attached graph/Cartesian topology

0x2

Epochs & Resource Lifecycle

One generalization — from a point event to an interval — turns out to cover three things that looked unrelated: request completion, RMA epochs, and handle lifecycle tracking.

mpi_isend → mpi_wait only needed a point event bound to a handle: local_complete, closed by one later call. RMA epochs (MPI_Win_start/post/complete/wait) need an interval: an unbounded number of Put/Get calls happen inside the bracket, none of them named at authoring time, and a transfer inside the bracket is only valid while both sides' epochs are open.

Three additions make that representable, without a predicate language:

  1. sync.events[].event_type — "open_epoch" / "close_epoch" (in addition to the plain point events already used for request completion), each optionally carrying epoch_scope: "access"｜"exposure" and a group_ref.
  2. data_flow[].valid_during — a list of {epoch_scope, bound_to, role} preconditions a transfer must fall inside.
  3. matching.kind: "group_match" — the epoch on one side is only well-formed if it pairs against a matching group on the other side.
Epoch kindMatchingGroup needed?Example
epoch.fencecollective_rendezvousNo — implicitly all ranks in the window's communicatorMPI_Win_fence
epoch.lock_unlocktrivial pairwiseNo — one origin, one targetMPI_Win_lock / unlock
epoch.pscwgroup_matchYes — explicit process groupMPI_Win_start/post/complete/wait

Resource lifecycle turns out to be the degenerate case of the same mechanism — an interval on a handle with no epoch pairing at all, just create → (any number of) use → destroy:

// mpi:mpi_win_create — semantics.formal.handle_lifecycle
[ { "handle": "param:win", "handle_kind": "WINDOW", "role": "create" } ]

// mpi:mpi_put — semantics.formal.handle_lifecycle
[ { "handle": "param:win", "handle_kind": "WINDOW", "role": "use" } ]

// mpi:mpi_win_free — semantics.formal.handle_lifecycle
[ { "handle": "param:win", "handle_kind": "WINDOW", "role": "destroy" } ]

Request completion (isend/wait) is now just handle_kind: "REQUEST" with no epoch fields attached — one vocabulary, three use cases (requests, RMA epochs, resource lifecycle), not three separate mechanisms.

What this does not do: "was every create eventually reached by a destroy" is a whole-program property. A single JSON entry can only supply the raw create/use/destroy facts at each call site — leak detection is the consuming tool's job, the same division of labor already drawn around tool_integration.invariants (no cross-entry constraints live in a single entry).
0x3

The Shape Catalog

Most communication ops cluster into a small number of canonical shapes. Reuse is mostly cross-PPM, not within one PPM — MPI's Bcast, NCCL's Broadcast, NVSHMEM's broadcastmem, and SHMEM's broadcast32 are the same shape wearing four different parameter lists.

A shape is a formal block with named placeholders (slots) instead of concrete param: refs. An entry doesn't author formal directly — it writes shape_ref plus a bindings map. A build step expands that against the shape's template and writes out a fully inlined formal block, identical in shape to everything shown in section 0x1.

Hard boundary: shapes are erased before anything ships. No consumer — not the code generator, not the race detector from section 0x5 — ever sees shape_ref. It exists purely to reduce what a human authors and diffs. If a consuming tool ever needed to understand shape_ref itself, that would mean the abstraction had leaked into the wrong layer.

Slot kinds

KindBinds to
buffer_slota param: ref of kind: BUFFER
extent_slot{count_ref, datatype_ref} pair of param: refs
selector_slota predicate in the reference grammar, e.g. rank == param:root
operation_slota param: ref of kind: OPERATION
handle_slota param: ref of kind: REQUEST or WINDOW
index_slotan expression describing a per-participant sub-extent (scatter, alltoall)
literal_slota plain enum/constant chosen at bind time, e.g. role: "create", epoch_scope: "access"

The escape hatch

Not everything fits a shape cleanly. An entry may combine shape_ref + bindings with an extra block, deep-merged onto the expansion after substitution — this is how mpi_isend gets its tag_match matching rule without polluting every other handle-bound shape that doesn't need tag matching:

{
  "shape_ref": "handle_bound.post_send",
  "bindings": { "buffer": "param:buf", "extent": {"count_ref":"param:count","datatype_ref":"param:datatype"}, "handle": "param:request" },
  "extra": {
    "sync.matching": { "kind": "tag_match",
      "match_keys": ["param:comm","param:tag","param:dest","self_rank_as_source"],
      "matched_across": "paired_call", "program_order_required": false }
  }
}

If more than a couple of entries need the same extra patch, that's the signal to promote it into its own shape rather than let extra quietly become a second place duplication hides.

0x5

Walking formal — a race detector, step by step

Grounded in one concrete consumer: the SPMD IR tool's data-race detector, catching a classic MBI-style bug — writing into a send buffer while a nonblocking send is still in flight.

MPI_Request req;
MPI_Isend(buf, count, MPI_INT, dest, tag, comm, &req);
buf[0] = 42;              // race: buf is still "owned" by the in-flight send
MPI_Wait(&req, &status);

buf[0] = 42 is ordinary local code — nothing in the schema describes it, and it shouldn't. What the schema describes is how long Isend keeps a claim on buf, and which call releases that claim.

The five-step walk

  1. Walk the IR; for each call to a modeled function, look up its semantics.formal. If null, skip — nothing to check.
  2. Evaluate participants[].selector to resolve which role this call site plays (usually trivial — a call the code itself makes is always self).
  3. For each data_flow entry belonging to that role, resolve buffer/extent to an IR value and size, and note the access kind. The access window opens here.
  4. Find where the window closes: if a sync event is bound_to a handle, dataflow-track that handle value in the IR until the call that consumes it and reaches its matching sync.ordering event. Otherwise the window closes at return.
  5. Flag a conflict if any IR memory access overlapping that buffer region falls inside the open window with no ordering edge to it, and at least one side is a write.

The trace

#Program pointWhat the tool doesWindow on buf
1MPI_Isend(buf, ...)Looks up mpi:mpi_isend.formal. One data_flow entry: read, param:buf. Opens a window.open: read
2same callhandle_lifecycle shows param:request, role create — tags the window with the IR value written into req.tagged with req
3buf[0] = 42;Ordinary IR store to buf. Is buf inside a currently open window? Yes.conflict candidate
4(window still open)Access kind = write; open window's kind = read; no ordering edge exists to this store.race flagged
5MPI_Wait(&req, ...)handle_lifecycle shows role: destroy for param:request; the tool matches req by dataflow and closes the window here.closes

The diagnostic — which buffer, which call opened the claim, which call closes it — comes straight out of data_flow and handle_lifecycle; the tool never special-cased Isend/Wait by name. Move the store after Wait and step 3 happens outside every open window — no conflict candidate is even generated.

One honest boundary: step 5 above still needs the compiler's own alias/points-to analysis to decide whether buf[0] really overlaps param:buf's extent. The schema's job stops at telling the tool when a window is open and on what region — it doesn't replace the tool's own memory model.

Open Questions & Non-Goals

Named plainly rather than quietly force-fit.

ItemStatusWhy it's open
shmem_int_wait_until and friends not modeled Value-dependent blocking — "wait until this memory location satisfies a runtime predicate" — has no representation in the current grammar. Adding it risks reopening the predicate-language door this whole layer was designed to avoid.
ncclGroupStart / ncclGroupEnd not modeled A context bracket with no handle attached — thread-local call-stack state rather than a value flowing through a parameter, so handle_lifecycle doesn't apply as written.
MPI_Type_commit-style state transition undecided Doesn't cleanly fit create/use/destroy — the handle stays valid but changes state, and using it before the transition is itself an error. A fourth role ("transition") is plausible but only one concrete case has been examined.
Resource leak / double-free detection out of scope for a single entry "Was every create eventually reached by a destroy" is a whole-program property. The schema supplies the create/use/destroy facts; a consuming tool decides what to do with them across the whole program.
Overlapping/nested epochs on one window not modeled What happens if a fence epoch and a lock epoch are (incorrectly) interleaved on the same window isn't represented — valid_during currently assumes well-nested, non-overlapping epochs.
Multi-GPU topology & transfer routing explicit non-goal Which physical device a pointer belongs to, and whether a transfer should go through GPUDirect RDMA versus a staged host copy, are backend/runtime routing decisions — not structural facts about the API symbol. memory_space (0x8) states what kind of memory; it deliberately stops short of how to move it.
Not a design flaw: every item above was surfaced by trying to write a concrete example and finding the vocabulary insufficient — which is the same process that produced reduce, tagged source, and handle_lifecycle in the first place. Better to log the gap than paper over it with a predicate language wide enough to swallow anything.
0x8

GPU Memory Spaces

execution.launch, execution.runs_on, and gpu_scope describe where a call executes. None of them say where the memory it touches actually lives — and that turns out not to be derivable from the others.

Why it's not derivable

The counterexample is CUDA-aware MPI. Its execution fields are unambiguous:

"execution": { "launch": "cpu", "runs_on": "cpu", "gpu_scope": null, "...": "..." }

Host-callable only, host-executed progress engine — nothing here suggests a GPU is involved. Yet buf in MPI_Send(buf, ...) can legally be a device pointer: a CUDA-aware implementation detects it and routes through GPUDirect RDMA or a staged copy instead of a plain host memcpy. Same symbol, same launch/runs_on, two entirely different data paths depending on what pointer value shows up at the call site. data_flow's buffer: "param:buf" gives a code generator no information about which path to emit.

CaseMemory spaceWhy
nvshmem_int_put's buffersalways symmetric_heapOnly symmetric-heap allocations can participate — structurally guaranteed by the model
A CUDA kernel's device-pointer argsalways deviceDevice code can't dereference an ordinary host pointer (barring managed memory)
MPI_Send's buf under CUDA-aware MPIhost or deviceGenuinely a property of the argument at the call site, not of the symbol

The memory_space field

Added to the parameter object — not to data_flow. Duplicating it into data_flow would create a second place it can drift out of sync with the one already-established rule that parameters stays the single source of truth for anything about an argument, referenced everywhere else via param:.

{ "name": "buf", "kind": "BUFFER", "direction": "in", "...": "...",
  "memory_space": "host" | "device" | "symmetric_heap" | "unified" | "either" | null }
ValueMeaning
hostOrdinary CPU-addressable memory
deviceGPU-resident memory, not host-addressable
symmetric_heapPGAS symmetric allocation — same logical offset resolves on every PE, no address translation needed the way an arbitrary device pointer would
unifiedCUDA unified/managed memory, addressable from either side
eitherNot fixed by the symbol — resolved at the call site; pairs with a tool_integration.context_dependencies entry
nullNot applicable (non-buffer parameters)

For the fixed cases, that single enum value is the whole story. For "either", the existing "not fixed by the symbol alone" mechanism from 0x4 — already built for NCCL's runtime-dependent blocking — covers it without new machinery:

{ "field": "param:buf.memory_space",
  "default_value": "host",
  "depends_on": ["pointer provenance of the argument bound to buf", "whether the MPI implementation was built with CUDA-aware support"],
  "note": "CUDA-aware MPI accepts a host or device pointer for the same symbol. Resolving which one requires the consumer's own pointer-provenance analysis — the same boundary already drawn for buffer-overlap in the race detector (0x5)." }

Non-goals

memory_space states what kind of memory a buffer lives in. It deliberately does not attempt two adjacent questions — logged as their own row in the 0x7 open-questions table rather than half-solved here: which physical GPU a device pointer belongs to in a multi-GPU node, and whether a transfer should be routed via GPUDirect RDMA or a staged host copy. Both are backend/runtime decisions, not structural facts about the API symbol — the same reasoning that already kept buffer-overlap resolution out of data_flow and left it to the compiler's own alias analysis in 0x5.

0xB

Cross-Cutting Patterns from the Full MPI Surface

Everything above was built and tested against a curated slice of MPI, NCCL, NVSHMEM, and SHMEM. This section is what changed after checking the vocabulary against the full ~450-symbol MPI standard — some patterns generalized cleanly, one only partially fit, and one is a genuine gap.

What generalized cleanly

MPI featureWhat it turned out to be
Persistent operations (_init + Start/Wait, including persistent collectives) The same handle_lifecycle interval from 0x2 — nothing said an epoch could only open and close once. Start re-opens, Wait re-closes, Request_free finally issues role: "destroy".
Nonblocking collectives (Iallreduce, Ibarrier, every I-prefixed collective) A collective shape plus a REQUEST handle are independent axes — composed with the same extra-patch mechanism already used for tag_match, not a new shape per combination.
Neighborhood collectives (Neighbor_allgather, Neighbor_alltoall, and their v/w/nonblocking/persistent variants) Zero new shapes. One new grammar built-in — is_neighbor(rank, comm) — and the existing gather/alltoall shapes cover the entire family via scope_selector.
Split collective I/O (File_write_at_all_begin/_end and its many siblings) The interval mechanism again, on a fourth handle kind. FILE and SESSION were added to handle_kind's enum in 0x4 — the mechanism itself needed nothing new.
Sessions (MPI-4's alternative to MPI_Init) Plain resource.lifecycle, same as a window or a communicator.

What partially fit

MPI_Accumulate and friends (Get_accumulate, Fetch_and_op, Raccumulate) are a reduce happening between exactly two parties — an origin's incoming value and a target's resident value — rather than across every participant in a collective. That's a real generalization of the reduce op worth keeping: a new inputs[].scope value, "rma_target_prior", referring to the target's own value rather than a sibling call-instance read. See the mpi_accumulate card in 0x6.

MPI_Compare_and_swap is the case that didn't fully transfer. SHMEM and NVSHMEM's compare-swap primitives take the swap value and comparand by value as scalar parameters; MPI's takes them as three separate local buffers (origin_addr, compare_addr, result_addr). Reusing the SHMEM-shaped rma.atomic binding for MPI's version would have silently dropped two of those buffers. Written out fully instead — see the mpi_compare_and_swap card — rather than forced into a shape that doesn't actually match.

Explicit non-goals, found by trying and stopping

MPI featureWhy it's out of scope
Generalized requests (MPI_Grequest_start, _complete, and the query/free/cancel callback triple) The whole point of a generalized request is that its completion semantics are arbitrary user code — there is no fixed data_flow to describe. formal stays null by construction, not by omission.
MPI Tools Interface (MPI_T_* — control variables, performance variables, events) Introspection into the MPI implementation itself, not communication between ranks. Same bucket as management/query calls already excluded in 0x0 — no data moves between participants at all.
Dynamic process management (MPI_Comm_spawn, Comm_accept, Comm_connect, Open_port) These create or attach new processes and change the reachable topology — a different axis entirely from data movement between an already-fixed participant set. handle_lifecycle's create role could name the new intercommunicator, but what's actually novel here (process creation) has nothing to do with what formal was built to express.

The one real gap: partitioned communication

MPI-4's partitioned point-to-point (Psend_init/Precv_init plus Pready/Pready_range/Pready_list/Parrived) splits one send buffer into independently-completable partitions. Every data_flow entry built so far describes one whole buffer with one completion event attached; nothing in the vocabulary lets a single entry's extent be sliced into sub-ranges that each get their own readiness state. This is logged as genuinely open in the mpi_psend_init card in 0x6, rather than quietly approximated by a shape that would misrepresent per-partition completion to both a code generator and a race detector.

The pattern holds: running the full standard through the vocabulary surfaced five things that generalized for free, one field that needed a genuinely new value, one shape that correctly failed to apply, and one honest gap — not a redesign. That ratio is closer to what "the vocabulary is right" should look like than a clean sweep would have been.
